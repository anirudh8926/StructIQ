# StructIQ

Graph-native engineering knowledge system. Lets an LLM solve and review structural
design problems grounded in IS 456, instead of doing flat semantic retrieval over a PDF.

## The one-sentence thesis
Two separate graphs — a **standards graph** (IS 456 clauses, limits, materials) and a
**design graph** (real members/spans/sections from an IFC model) — are joined inside
Cognee. Compliance checks traverse from a real member to its governing clause and return
a verdict **with the clause path**. That join is the entire product.

## What this is NOT
- Not autonomous design ("design me a building"). Scope is bounded design assistance +
  compliance review for known problem classes.
- Not a chatbot wrapper. The differentiator is structured multi-hop traversal +
  auditable reasoning path, shown against flat RAG.

## Architecture
```
IS 456 PDF  -> standards graph ─┐
                                ├─> one Cognee graph -> compliance traversal -> verdict + clause path
IFC model   -> design graph ────┘
```

## Ontology (6 entities — the spine of everything)
Defined in src/structiq/ontology.py as Pydantic models:
- Material      (name, grade, yield_strength, use_conditions)
- Member        (type, cross_section, span, support_conditions)
- LoadCase      (load_type, magnitude, combination)
- DesignCode    (code_name, clause_id, formula, applicability)
- SafetyFactor  (value, condition, referenced_by)
- Connection    (member_a, member_b, relationship_type)

A parsed IfcBeam/IfcColumn becomes a Member node. A parsed clause becomes a DesignCode node.

## Stack
- cognee            — graph + vector memory layer (custom ontology)
- ifcopenshell      — parse IFC structural members
- pdfplumber        — parse IS 456 (tables matter, hence pdfplumber not pymupdf)
- chromadb + sentence-transformers — the FLAT-RAG BASELINE for the contrast demo
- fastapi           — thin query API (/upload, /check, /model, /baseline)
- (UI) Vite + React + react-three-fiber — full 3D model of the frame, members painted
  green/red by compliance, click-to-inspect shows the clause path in 3D

## The two demo files
`scripts/make_demo_ifc.py` emits BOTH IFCs from one frame definition:
- data/ifc/frame_clean.ifc  — fully compliant (B3 rebar 4-T16)
- data/ifc/frame_flawed.ifc — one planted violation (B3 rebar 2-T10, fails Cl 26.5.1.1)
Identical geometry; they differ in exactly one property (B3 rebar). Upload clean -> all
green; upload flawed -> B3 red. The contrast IS the demo.

## Demo moment
Upload frame_clean.ifc -> 3D frame all green. Upload frame_flawed.ifc -> "check against
IS 456" -> B1 ✓, B2 ✓, B3 ✗ fails Cl 26.5.1 (min tension steel). Click B3 -> InspectPanel
shows the clause path in 3D. Side-by-side vs flat RAG.

## Conventions for Claude Code
- Keep compliance LOGIC in the per-code modules under src/structiq/standards/ (e.g.
  is456.py), not in the API layer and not in compliance.py. compliance.py is pure graph
  traversal + verdict assembly; the API only exposes it. Writing design rules in a fastapi
  route or in compliance.py is the wrong layer.
- Standards are pluggable. To ADD a code: create src/structiq/standards/<code>.py, build a
  `Standard` (materials, clauses, factors, governs map, checks), call `register(std)`, and
  import it from standards/__init__.py. graph.py and compliance.py iterate the registry
  generically and need no change. STRUCTIQ_CODES (env) narrows which codes are active.
- The demo IFCs are GENERATED by scripts/make_demo_ifc.py with one planted violation. Put
  dimensions + coordinates in an explicit property set (Pset_StructIQ) so we read them
  directly and skip IFC geometry math.
- The frontend lives in frontend/ (Vite + react-three-fiber). The GET /model JSON is the
  single backend<->frontend contract — change both sides together.
- If Cognee auto-extraction produces a messy standards graph, prefer hand-authoring ~30
  demo-critical nodes over trusting full auto-extraction. A small correct graph wins.
- Don't add features not in the build order without flagging the tradeoff against the 4-day clock.
